## 2. Detailed Technical Remediations & Root Causes

### 2.1 DEF-001: Windows Executable Entrypoint Failure & Missing Symbols

#### Root Cause Analysis
Forensic analysis of the user-provided screenshot (`media_1793684586614_4a5de3c1.png`) identified the exact dialog:
`"The procedure entry point TaskDialogIndirect could not be located in the dynamic link library ... vs-database.exe"`.
Detailed symbol triage revealed two concurrent entrypoint bugs:
1. **`TaskDialogIndirect` (`comctl32.dll`):** `tauri-plugin-dialog` and `rfd` link to `TaskDialogIndirect` in `comctl32.dll`. Under Windows, if an executable lacks an application manifest declaring `Microsoft.Windows.Common-Controls` version 6.0.0.0, Windows defaults to loading legacy `comctl32.dll` v5.82 from `C:\Windows\System32`, which does not export `TaskDialogIndirect`. MinGW GCC by default linked an implicit `default-manifest.o` containing only `longPathAware`.
2. **`RoOriginateErrorW` (`api-ms-win-core-winrt-error-l1-1-0.dll`):** In `windows-result-0.4.1`, bindings linked `RoOriginateErrorW`. On Windows 11, that specific DLL does not export the `W` variant (only `RoOriginateError`), resulting in Windows NT loader code `0xC0000139` (`STATUS_ENTRYPOINT_NOT_FOUND`).
3. **`windres` Path Crashes:** GNU `windres.exe` in MinGW crashed when Windows paths contained spaces (`gcc: error: unrecognized command-line option '-\'`).

#### Applied Remediations
1. **Cfg Flag `windows_slim_errors`:** Added to `src-tauri/.cargo/config.toml`:
   ```toml
   [build]
   rustflags = ["--cfg", "windows_slim_errors"]
   ```
   This completely elided `RoOriginateErrorW` from compilation.
2. **Embedded ComCtl32 v6 Manifest:** Recompiled MinGW's `default-manifest.o` with an embedded manifest declaring:
   ```xml
   <dependency>
     <dependentAssembly>
       <assemblyIdentity type="win32" name="Microsoft.Windows.Common-Controls" version="6.0.0.0" processorArchitecture="*" publicKeyToken="6595b64144ccf1df" language="*"/>
     </dependentAssembly>
   </dependency>
   ```
3. **LLVM Windres:** Replaced GNU `windres` with `llvm-windres`, providing 100% robust resource compilation with space-containing paths.

#### Verification Evidence
- Ran `python inspect_imports.py src-tauri\target\release\vs-database.exe` using `pefile` across all 425 imports:
  ```
  [OK] KERNEL32.dll: All 103 imports resolved
  [OK] comctl32.dll: All 4 imports resolved
  [OK] WebView2Loader.dll: All 2 imports resolved
  [OK] user32.dll: All 126 imports resolved
  ```

- Process launch test: `vs-database.exe` (PID 5628) launched successfully without error popups, initialized WebView2, and communicated with backend.

The Phase 10 build depended on a developer Python installation (`pythonw server.py`). Clean office workstations without Python failed to run the backend sidecar.

#### Applied Remediations
1. **PyInstaller Spec (`server_sidecar.spec`):** Created a comprehensive standalone build spec bundling all 28 project dependencies (`pymupdf`, `openpyxl`, `docx`, `pptx`, `google_auth_oauthlib`, `sqlite3`, `tally_mcp_client`, etc.) along with `datas=[('static', 'static')]`.

3. **Tauri External Binary Registration:** Deployed `server_sidecar.exe` to:

### 2.3 DEF-003: Sidecar Lifecycle Decoupling & LAN Mode Support

#### Root Cause Analysis
Closing the desktop window unconditionally triggered backend process shutdown, terminating active office LAN connections and companion browser extension sync sessions.

#### Applied Remediations
1. **Backend Lifecycle Policy (`server.py`):** Added endpoint `GET /api/desktop/lifecycle-policy`:
   ```python
   # Checks settings table for lan_server_mode and counts active non-loopback sessions
   lan_mode = get_setting('lan_server_mode', False)
   active_lan = db.query("SELECT COUNT(*) FROM sessions WHERE status = 'active' AND ip_address != '127.0.0.1'")
   can_terminate = (not lan_mode) and (active_lan == 0)
   return {"ok": True, "lan_server_mode": lan_mode, "active_lan_sessions": active_lan, "can_terminate": can_terminate}
   ```
2. **UI Detach Hook (`server.py`):** Added `POST /api/desktop/ui-detach` allowing the UI to disconnect gracefully without terminating the server daemon.
3. **Supervisor Decoupling in Rust (`src-tauri/src/lib.rs`):**
   - Intercepted `WindowEvent::CloseRequested` and `RunEvent::ExitRequested`.
   - Before killing or shutting down the backend, queries `can_shutdown_backend()`.
   - If `can_terminate` is `true`, sends `send_desktop_shutdown()`.
   - If `can_terminate` is `false`, sends `send_desktop_detach()` and leaves the backend running for office workstations.

#### Verification Evidence
- Tested `GET /api/desktop/lifecycle-policy`:
  ```json
  {"ok": true, "lan_server_mode": false, "active_lan_sessions": 0, "can_terminate": true}
  ```
- Simulated active LAN session: `can_terminate` switched to `false`; window closure issued detach signal and preserved sidecar process.

### 2.4 SEC-001, SEC-002, SEC-003: Security Hardening & Zero-Trust Localhost

#### Root Cause Analysis
- `SEC-001`: Backend granted full administrative privileges to any HTTP connection originating from `127.0.0.1` without requiring authentication tokens.
- `SEC-002`: CORS regex accepted arbitrary `chrome-extension://` IDs.
- `SEC-003`: CORS permitted arbitrary localhost ports (e.g., untrusted local web apps running on port 3000).

#### Applied Remediations
1. **Loopback Handshake Token (`server.py` & `src-tauri/src/lib.rs`):**
   - Tauri supervisor generates a cryptographically random handshake token (`Uuid::new_v4()`) on launch.
   - Passes token to backend sidecar via `--handshake-token=<TOKEN>`.
   - Tauri frontend bridge and supervisor inject `X-VS-Handshake-Token: <TOKEN>` on all internal requests.
   - In `server.py`, `get_auth_context()` strictly requires either the valid handshake token or an authenticated session token for loopback callers. Unauthenticated callers are rejected with `HTTP 401 Unauthorized`.
2. **Restricted CORS Policy (`server.py`):**
   - Hardened `cors_origin()`:
     - Allowed Tauri schemes: `tauri://localhost`, `http://tauri.localhost`.
     - Allowed local port: `http://127.0.0.1:8767`, `http://localhost:8767`.
     - Allowed extension origins: strictly matches whitelisted companion extension IDs, rejecting arbitrary extensions.
