## 3. Business Categorization of the Variance

### Category 1: Legacy-Only Business Records (2,551 Rows in Legacy)
- **What they are:**  
  While the Tauri migration was being engineered and audited, the legacy desktop app continued serving office accounting staff on port `8767`. During this operational period, staff processed **2 additional bank statement import sessions** (`automation_import_sessions` 25 and 26). This produced:
  - 1,498 raw bank transaction lines (`automation_transactions`)
  - 749 double-entry posting allocations (`automation_posting_records`)
  - 298 learned company ledger rules (`automation_company_learning`)
  - 3 custom mapping rules (`automation_mapping_rules`)
  - 1 activity log entry (`activity_log`)
- **Business Impact:**  
  These records represent genuine client accounting work performed in the legacy software after the initial V2 migration branch was created.
- **Migration Relevance:**  
  **HIGH.** When the final cutover occurs, these 2,551 records must be brought forward into V2 so that staff do not lose the bank reconciliations performed in recent weeks.

### Category 2: V2 Test-Generated Records (18 Rows in V2)
- **What they are:**  
  During Phases 11 through 14B, staging and soak test scripts created:
  - 8 test device entries (`devices`)
  - 8 test session tokens (`sessions`)
  - 2 test user accounts (`users`)
- **Business Impact:**  
  These records are purely synthetic test artifacts generated by automated test runners (`test_host_and_twopc_cutover.py`, `phase14a_observation_engine.py`).
- **Migration Relevance:**  
  **EXCLUDE.** These records must NOT be merged into production. They should be purged or left isolated in the staging environment.

## 4. Executive Decision Options for Management

Management and the Lead Chartered Accountant must choose one of the following three migration strategies prior to final production cutover:

### Option A: Clean Incremental Delta Import (Recommended)
- **Procedure:**  
  1. Freeze the legacy application at cutover time.
  2. Run the verified row-level script [`migrate_pilot_records.py`](file:///D:/AntiGravity%20Automation/VS%20Database%202.0%20-%20Tauri%20Migration/migrate_pilot_records.py) with `--mode=delta-import`.
  3. Extract only the 2,551 post-branch legacy records (`import_sessions`, `transactions`, `postings`, `learning`) and insert them into V2 using SQLite transactions.
  4. Purge the 18 synthetic test records from V2.
- **Advantages:**  
  - Zero data loss for recent accounting transactions.
  - Foreign key constraints strictly validated during insertion.
  - 22 historical orphan records preserved.
  - V2 performance optimizations and clean configuration retained.
- **Risk:** Requires ~2 minutes of maintenance downtime at cutover.

### Option B: Fresh Production Baseline Reseed (Alternative)
- **Procedure:**  
  1. Freeze legacy application at cutover.
  2. Take a fresh, certified snapshot of the complete legacy database (all 15,669 rows).
  3. Apply the V2 schema migration scripts and performance indexes directly to this fresh copy.
  4. Place the newly migrated copy into V2 `data/vs_database_desktop.db`.
- **Advantages:**  
  - 100% bit-for-bit capture of legacy state up to the second of cutover.
  - Automatically includes all 2,551 recent records.
- **Risk:** Requires re-running the automated functional test suite against the reseeded database before launching.

### Option C: Isolated Staging Continuation (Current Status Quo)
- **Procedure:**  
  - Keep V2 running exclusively against its current 13,136-row working database during observation.
  - Do not copy or import any records until all observation phases are formally signed off.
- **Advantages:**  
  - Zero risk to either legacy production or V2 stability.
  - Keeps observation and cutover strictly separated.
- **Recommendation:** **Adopt Option C for Phase 14C Observation, then execute Option A upon final cutover approval.**
